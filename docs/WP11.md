# WP11: Attack Analysis Tab — Pipeline Fix & DB Writer Bug

This document describes the root-cause investigation and all fixes applied to get the **Attack Analysis** dashboard tab to display real prediction data.

---

## Problem Statement

The Attack Analysis tab loaded successfully in the UI but displayed **no data** — all KPIs showed `—` and the charts were blank. The backend API (`/api/analysis/summary`) returned `total_segments: 0` because the `gcn_predictions` table in TimescaleDB was empty, despite the `metrics` table containing 19,500 rows from previous experiment runs.

---

## Root Cause Chain

The failure was a chain of three independent bugs:

```
NS-3 → Kafka (wifi7.telemetry.v0_1)
              ↓
         [BUG 1] Windowizer set to latest offset → reads 0 messages
              ↓ (no segments produced)
    Kafka (wifi7.ml.windowed_features.v1)
              ↓
         [BUG 2] GCN Detector set to latest offset → reads 0 segments
              ↓ (inference never runs)
         [BUG 3] db_writer idle-in-transaction → writes silently discarded
              ↓
    gcn_predictions table: 0 rows
              ↓
    Dashboard Attack Analysis tab: blank
```

---

## Bug 1 — Windowizer: `auto_offset_reset: latest`

**File:** `security/detector/windowizer/config.yaml`

**Problem:** The Windowizer consumer group (`windowizer-gcn-v1`) had no committed offsets because it had never successfully consumed. With `auto_offset_reset: latest`, it started reading from the *current end* of the `wifi7.telemetry.v0_1` topic, skipping all 19,500 historical messages.

```
TOTAL-LAG: 19500
CURRENT-OFFSET: -   ← never committed, starts from latest
```

**Fix:**
```yaml
# Before
auto_offset_reset: latest

# After
auto_offset_reset: earliest
```

---

## Bug 2 — GCN Detector: `auto_offset_reset: latest`

**File:** `twin/gnn/detector/config.yaml`

**Same issue as Bug 1.** The GCN detector consumer group (`gcn-detector-v1`) also had no committed offsets and was configured to start from `latest`, so it never received any windowed segments even after the Windowizer started producing them.

**Fix:**
```yaml
# Before
auto_offset_reset: latest

# After
auto_offset_reset: earliest
```

---

## Bug 3 — `db_writer.py`: idle-in-transaction leaving writes invisible

**File:** `twin/gnn/detector/db_writer.py`

**Problem:** `check_connection()` called `self.cursor.execute("SELECT 1")` without ever calling `fetchone()`. In psycopg2 with `autocommit=False` (the default), this opened a transaction and left the connection permanently in the PostgreSQL state `idle in transaction`. Subsequent prediction writes went into this open transaction, but `commit()` was not reliably called in a clean state, silently discarding inserts. Verified via:

```sql
SELECT pid, state, wait_event, query FROM pg_stat_activity WHERE datname='udr' AND state != 'idle';
-- pid 228 | idle in transaction | ClientRead | SELECT 1
```

**Fix:** Replaced the cursor-based check with `connection.closed + connection.poll()`, and switched `flush()` to create a **fresh cursor per flush** using a context manager:

```python
# Before (BROKEN)
def check_connection(self):
    self.cursor.execute("SELECT 1")   # opens transaction, never committed
    return True

def flush(self):
    execute_batch(self.cursor, insert_query, values)   # shared, stale cursor
    self.connection.commit()

# After (FIXED)
def check_connection(self):
    if self.connection is None or self.connection.closed != 0:
        return False
    self.connection.poll()   # lightweight check, no transaction opened
    return True

def flush(self):
    with self.connection.cursor() as cursor:   # fresh cursor, no state leak
        execute_batch(cursor, insert_query, values)
    self.connection.commit()
```

Also removed the persistent `self.cursor` attribute entirely since all operations now use short-lived context-manager cursors.

## Prevention Notes

- **Always use `auto_offset_reset: earliest`** for pipeline services that may restart or whose consumer group offsets may be cleared. Use `latest` only for live-only consumers where replaying history is undesirable.
- **Never use `cursor.execute()` for connection health checks** in psycopg2 without `autocommit=True`. Prefer `connection.closed`, `connection.poll()`, or a dedicated connection in autocommit mode.
- **After rebuilding a pipeline image**, always delete the corresponding Kafka consumer group before restarting so the new `auto_offset_reset` setting takes effect.

```bash
# Reset a consumer group so offset.reset applies
rpk group delete <group-id>
docker compose -f docker-compose.pipeline.yml restart <service>
```
